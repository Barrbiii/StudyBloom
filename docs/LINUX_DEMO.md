# Демонстрация StudyBloom в Linux VM (UTM)

Актуально на 24 ноября 2026. Выбран UTM на MacBook; UTM уже установлен,
гостевой Linux ещё не установлен. Эти инструкции не подтверждают развёртывание
на пользовательском Mac: доступа к нему в текущей среде нет.
Docker в CI работает на Ubuntu; доступ преподавателя к VM проверяется отдельно.

## 1. Гостевая система

1. На Mac проверь «Об этом Mac»: чип Apple M-серии или процессор Intel.
2. Для Apple Silicon выбирай Ubuntu Server ARM64; для Intel — Ubuntu AMD64.
   Не выбирай x86-эмуляцию на Apple Silicon для обычного запуска проекта.
3. В UTM создай VM: Virtualize → Linux → ISO подходящей архитектуры.
   Начальные ресурсы: 2–4 CPU, 4GB RAM, диск40GB, если свободные ресурсы Mac позволяют.
   Это ориентир проекта; можно увеличить при нехватке памяти сборки.
4. Установи Ubuntu LTS в виртуальный диск, извлеки ISO и перезагрузи гостя.
   Серверной системы достаточно: браузер можно открыть на Mac, контейнеры работают в Linux.

Официальные инструкции: [UTM Ubuntu](https://docs.getutm.app/guides/ubuntu/),
[образы Ubuntu Server](https://ubuntu.com/download/server).
Инструкция UTM может показывать более старую версию Ubuntu: используй пункты
своей установленной версии UTM и подходящую архитектуру, не копируй номера вслепую.

## 2. Docker внутри Linux

Установи Docker Engine и Compose plugin по [официальной инструкции Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
Проверки выполняются в гостевом Linux, а не в терминале macOS:

```bash
uname -srm
docker --version
docker compose version
docker info
```

Если нет прав на сокет Docker, используй предусмотренный инструкцией вариант
прав доступа. Не открывай Docker API в сеть и не меняй сокет на всем доступный.

## 3. Запуск проекта

```bash
git clone https://github.com/Barrbiii/StudyBloom.git
cd StudyBloom
docker compose up --build -d --wait
docker compose ps
curl --fail http://localhost:5173/api/health
```

Интерфейс в Linux: http://localhost:5173. API-документация в Linux:
http://localhost:8000/docs. Backend опубликован только на127.0.0.1 гостя,
PostgreSQL наружу не опубликован. Nginx проксирует `/api` на том же5173.
Создай личный аккаунт в интерфейсе; данные прежних тестовых записей без владельца
сохранены отдельно и автоматически не присваиваются новому аккаунту.

## 4. Доступ с Mac и устройства преподавателя

В Linux посмотри адреса через `hostname -I`. В зависимости от сетевого режима UTM
доступ по `http://IP_ГОСТЯ:5173` может работать только с Mac. Это ещё не проверка
доступа преподавателя из общей сети точки доступа.

Если VM не доступна со второго устройства, настрой поддерживаемый выбранным backend
UTM проброс TCP5173 с Mac на гостевой5173 либо подходящий сетевой режим. Для проброса
нужно разрешить доступ по локальному сетевому адресу Mac, а не только127.0.0.1.
Тогда преподаватель открывает `http://IP_MAC:5173`. Порт8000 пробрасывать не нужно.
Разрешай вход только в нужной локальной сети; не отключай брандмауэр целиком.
До защиты обязательно открой приложение с реального второго устройства.

Для локальной HTTP-демонстрации Compose использует AUTH_COOKIE_SECURE=false.
Публичное размещение через интернет требует HTTPS, secure cookie и отдельной настройки;
инструкция локальной защиты не является готовой инструкцией публичного хостинга.

## 5. Контрольный сценарий

1. Зарегистрироваться и войти. Создать задачу с приоритетом и найти её фильтром.
2. Создать предмет, дедлайн и событие; открыть месяц/неделю, изменить дату.
3. Добавить занятие, проверить время/аудиторию/преподавателя и обзор сегодняшнего дня.
4. Запустить Pomodoro на1 минуту, проверить паузу/reload, затем завершить и сохранить.
5. Создать привычку с целью, поставить отметку, проверить серию и график концентрации.
6. Выйти и войти вторым аккаунтом: чужие данные не должны отображаться.
7. Обновить страницу; затем `docker compose restart backend` — данные сохраняются.
8. Остановить `docker compose down`, запустить снова `docker compose up -d --wait`,
   войти прежним аккаунтом и проверить записи. Не используй флаг `-v`: он удаляет том.
9. Открыть сервис со второго устройства и сохранить снимок результата для защиты.

В одноразовом тестовом окружении доступен полный автоматический smoke-test:
`STUDYBLOOM_SMOKE=1 python3 scripts/verify-compose.py`. Он создаёт отдельный случайный
тестовый аккаунт, проверяет модули и перезапускает backend; существующие записи не удаляет.
Используй CI/тестовый экземпляр: для обычной защиты достаточно контрольного сценария выше.

## Обновление и диагностика

`bash scripts/update.sh` проверяет чистоту рабочей копии и ветку main, получает изменения
без переписывания истории, пересобирает контейнеры. Изменения в GitHub сами по себе
не обновляют уже запущенные контейнеры на Mac/VM.

При ошибке: `docker compose ps`, `docker compose logs --tail=100 backend frontend db`.
Не публикуй секреты или персональные данные из логов. Docker и VM нужны включёнными
во время локального запуска/демонстрации; постоянно держать их включёнными не требуется.
